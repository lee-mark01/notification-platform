# 0002. 전달 보장은 at-least-once, 멱등성은 3계층

- 상태: 채택 (2026-10-08)
- 관련: [상태 머신](../design/state-machine.md), [ERD](../design/erd.md#idempotency_key-phase-2), 장애 시나리오 1·6

## 상황

알림은 API 접수 → DB 저장 → 큐 → Worker → Provider(SES·FCM)를 거친다. 어디서든 장애가 날 수 있고, 클라이언트도 응답을 못 받으면 같은 요청을 다시 보낸다. "정확히 한 번" 보내는 것이 이상적이지만, Provider 호출은 성공했는데 응답을 받기 전에 Worker가 죽으면 우리는 성공 여부를 알 수 없다. SES·FCM API에는 같은 요청을 한 번만 처리해 주는 멱등 키가 없다.

## 선택지

| 선택지                                          | 장점             | 단점                                                       |
| ----------------------------------------------- | ---------------- | ---------------------------------------------------------- |
| A. at-least-once: 성공 기록 전 장애면 다시 보냄 | 알림을 잃지 않음 | 드물게 중복 발송                                           |
| B. at-most-once: 보내기 전에 "보냄"으로 기록    | 중복 없음        | 장애 시 알림 유실. 인증 메일이 사라지면 사용자는 가입 불가 |
| C. exactly-once                                 | 이상적           | Provider가 멱등 키를 지원하지 않아 불가능                  |

## 결정

A. 그리고 중복이 생기는 구간을 계층마다 최소화한다.

1. **요청 계층**: `Idempotency-Key` + (클라이언트, 키) 유니크 + 본문 해시. 키를 먼저 IN_PROGRESS로 커밋하고(`locked_until`), 알림 생성과 응답 저장을 두 번째 트랜잭션에서 한다. 같은 키·같은 본문은 저장된 응답, 다른 본문은 422, 처리 중은 409.
2. **큐 계층**: `jobId = notificationId`로 같은 알림의 job이 중복 등록되지 않게 한다. 단, 완료된 job이 `removeOnComplete`로 지워지면 같은 jobId로 다시 등록될 수 있으므로 최종 방어선은 아니다.
3. **발송 계층**: 조건부 상태 전이로 같은 알림을 두 Worker가 동시에 잡지 못하게 한다. 점유에 `lease_until`을 두어, 살아 있는 Worker의 작업은 건드리지 않고 죽은 Worker의 작업만 이어받는다.

## 결과

- 남는 중복 구간: Worker가 Provider 호출을 끝낸 직후, `SENT`를 기록하기 전에 죽는 경우. 이 경우만 lease 만료 후 한 번 더 발송된다. 장애 시나리오 6에서 `kill -9`로 재현해 실제 중복 횟수를 측정·기록한다.
- 인증 메일처럼 중복보다 유실이 치명적인 알림에 맞는 선택이다. 마케팅 메일의 드문 중복은 감수한다.
- 클라이언트는 응답을 못 받으면 같은 `Idempotency-Key`로 안전하게 재시도할 수 있다.

## 이 결정이 바뀌는 조건

- Provider가 멱등 키(예: 요청 id로 중복 제거)를 지원하면, 발송 계층의 남은 중복도 Provider가 막아 사실상 exactly-once가 된다.
- 중복이 유실보다 훨씬 나쁜 알림(예: 결제 완료 후 "포인트 지급"처럼 받은 쪽이 행동을 하는 메시지)을 다루게 되면, 그 유형만 at-most-once로 다르게 처리하거나 수신 측이 멱등하게 만들어야 한다.
