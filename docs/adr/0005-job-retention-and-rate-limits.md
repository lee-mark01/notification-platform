# 0005. job 보존 정책과 큐별 발송 속도 제한

- 상태: 채택 (2026-10-09, Phase 5)
- 관련: [ADR-0001 큐 분리](0001-queue-routing.md), [ADR-0002 멱등성](0002-delivery-guarantee-and-idempotency.md), [ADR-0003 Sweeper](0003-sweeper-over-outbox.md)

## 1. 끝난 job을 얼마나 남길까

### 상황

BullMQ는 같은 `jobId`의 job이 Redis에 남아 있으면 `add()`를 무시한다. 이 프로젝트는 `jobId = notification-{id}`라서, 끝난 job을 오래 남길수록 "같은 알림을 두 번 넣는" 경우를 큐가 먼저 걸러 준다. 반대로 오래 남길수록 Redis 메모리를 쓴다. 대량 발송(PR #73)이 들어오면서 큐 하나에 하루 수만 건이 쌓일 수 있게 됐다.

### 선택지

| 선택지                                  | 장점                                                     | 단점                                                            |
| --------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| A. 바로 지움 (`removeOnComplete: true`) | 메모리 최소                                              | jobId 중복 제거가 사실상 없음. 실패 원인을 Redis에서 볼 수 없음 |
| B. 기간 + 개수 상한                     | 중복 제거 창과 디버깅 여지를 남기면서 메모리 상한이 있음 | 상한을 넘으면 창이 짧아짐                                       |
| C. 오래 보관 (상한 없음)                | 큐만 봐도 이력이 다 있음                                 | 장애(바운스 폭주) 때 메모리가 계속 늘어 Redis 자체가 위험       |

### 결정

B. 큐마다 완료 job은 24시간·최대 10,000개, 실패 job은 7일·최대 10,000개. DLQ의 job은 처리하는 Worker가 없어 대기 상태로 남고, redrive가 지운다.

### 이유

- **중복 제거의 최종 방어선은 Redis가 아니라 DB다.** job이 지워진 뒤 같은 알림이 다시 등록돼도 Worker의 조건부 점유(`PENDING`·`QUEUED`·`RETRYING`이거나 lease가 끝난 `SENDING`일 때만 점유)가 두 번째 발송을 막는다. 그래서 보존 기간은 정확성이 아니라 효율(쓸데없는 job 실행을 줄임)과 디버깅을 위한 값이다.
- 이력은 이미 DB에 있다(`notification` 상태, `delivery_attempt` 시도마다 1행). Redis에 오래 남길 이유가 없다.
- 개수 상한은 장애 때를 위한 것이다. 1만 건 마케팅이 잘못된 주소 목록으로 나가면 실패 job이 한꺼번에 쌓인다.
- 실패 job을 완료 job보다 오래 두는 이유: 사람이 원인을 볼 시간이 필요하다(주말 포함 7일).

### 이 결정이 바뀌는 조건

- 하루 발송량이 수백만 건이면 개수 상한이 몇 분치밖에 안 된다. 그때는 상한을 그대로 두고 "큐에서 중복 제거"는 기대하지 않는다. 결과는 같다(DB가 막음).
- 외부 Provider가 멱등 키를 지원하면 중복 방어가 Provider 쪽으로 한 겹 더 생겨 보존 기간을 더 줄여도 된다.

## 2. 큐별 발송 속도 제한

### 상황

외부 Provider에는 초당 한도가 있다. SES는 **계정 전체**에 하나의 초당 발송 한도가 있고(샌드박스 1건, 프로덕션 시작 시 보통 14건), 넘으면 스로틀링 오류를 돌려준다. 이메일 큐는 거래성과 마케팅 두 개라서, 각 큐가 한도까지 쓰면 합이 한도의 두 배가 된다.

### 선택지

| 선택지                                                   | 장점                                                                                                      | 단점                                                                                            |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A. 제한 없음, 스로틀링은 일시 오류로 재시도              | 구현 없음                                                                                                 | 마케팅 폭주가 한도를 다 쓰면 인증 메일도 스로틀링을 맞고 재시도 대기로 밀림. 재시도 횟수를 낭비 |
| B. 채널 한도를 두 큐에 고정 비율로 나눠 BullMQ `limiter` | 거래성 몫이 항상 보장됨. 설정만으로 끝남. limiter는 같은 큐의 모든 Worker가 공유해 인스턴스가 늘어도 유지 | 거래성이 한가할 때 그 몫은 놀게 됨                                                              |
| C. Redis에 채널 공용 토큰 버킷 + 우선순위                | 한도를 남김없이 씀                                                                                        | 직접 구현해야 하고, 공정성·우선순위 로직이 생김                                                 |

### 결정

B. `EMAIL_RATE_PER_SEC`(기본 14), `PUSH_RATE_PER_SEC`(기본 1,000)를 `TRANSACTIONAL_RATE_SHARE`(기본 0.3) 비율로 나눈다. 두 큐의 합은 채널 한도를 넘지 않고, 각 큐는 최소 초당 1건이다. 계산은 `src/queue/rate-limits.ts` 순수 함수.

### 이유

- 큐를 나눈 목적(ADR-0001)이 "마케팅 폭주 중에도 인증 메일이 밀리지 않게"다. 한도를 나눠 갖지 않으면 큐는 분리돼 있어도 Provider 앞에서 다시 섞인다.
- 놀게 되는 몫(기본 30%)은 인증 메일의 대기 시간을 보장하는 비용으로 본다. 지금 규모에서는 C의 복잡도가 이득보다 크다.
- 한도를 넘는 경우(설정 실수, 다른 시스템과 계정 공유)는 여전히 스로틀링 → 일시 오류 → 백오프 재시도로 처리된다(ADR-0002 오류 분류).

### 증거

- `test/queue/rate-limit.e2e-spec.ts`: 거래성 큐 초당 2건으로 6건을 보내면 첫 job과 마지막 job의 시작 간격이 1.8초 이상, 어느 연속 3건도 0.9초 안에 시작하지 않는다. 같은 테스트를 limiter 없이(한도 10,000) 돌리면 간격은 0.17초로 실패한다.

### 이 결정이 바뀌는 조건

- 발송량이 한도에 늘 붙어 있어 놀리는 몫이 비용이 되면 C(공용 토큰 버킷)로 간다.
- 스로틀링 응답을 받았을 때 그 큐 전체를 잠시 멈추고 싶으면 BullMQ `worker.rateLimit(ms)` + `Worker.RateLimitError()`로 동적 제한을 더한다. 지금은 job 하나가 백오프로 물러난다.
- SES 샌드박스(초당 1건)에서는 최소값 2가 한도를 넘는다. 실험 규모에서는 스로틀링 재시도로 감수한다.
