# 0004. ORM으로 TypeORM 사용

- 상태: 채택 (2026-10-07, Phase 0에서 도입)
- 관련: [ERD](../design/erd.md)

## 상황

NestJS + MySQL에서 엔티티 매핑, 마이그레이션, 그리고 이 프로젝트의 핵심인 **조건부 UPDATE와 영향 행 수 확인**을 다룰 ORM이 필요하다. 공고 우대사항은 "TypeORM·Prisma 등 ORM 사용과 마이그레이션 운영"이다.

## 선택지

| 선택지                      | 장점                                                                                                                                                               | 단점                                                                                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. TypeORM                  | 데코레이터 엔티티라 JPA와 개념이 거의 1:1. `@nestjs/typeorm` 공식 모듈. QueryBuilder로 조건부 UPDATE와 `affected` 확인이 자연스러움. 엔티티 기반 마이그레이션 생성 | 타입 안전성이 Prisma보다 약함(QueryBuilder 문자열). 버전별 동작 차이가 있어 문서 확인 필요                                                                        |
| B. Prisma                   | 스키마 파일에서 생성한 클라이언트의 타입 안전성이 강함. 개발 경험 좋음                                                                                             | 엔티티 클래스가 아니라 생성된 클라이언트 중심이라 NestJS DI·도메인 모델과 결합 방식이 다름. 공식 Nest 모듈은 없음. 세밀한 조건부 갱신은 `updateMany` 또는 raw SQL |
| C. 쿼리 빌더(Knex, Drizzle) | SQL에 가깝고 가벼움                                                                                                                                                | 엔티티·마이그레이션 생성 같은 ORM 기능을 직접 구성                                                                                                                |

## 결정

A. TypeORM 1.x + `mysql2`, `synchronize: false`, 마이그레이션은 엔티티에서 생성하고 CI에서 스키마 드리프트를 검사한다.

## 결과

- Java/Spring(JPA) 경험을 그대로 옮길 수 있어 학습 비용이 가장 낮다(`@Entity`, `@Version`, Repository).
- 조건부 UPDATE: `createQueryBuilder().update().where(...).execute()`의 `affected`로 "영향 행 0이면 중단"을 구현한다(템플릿 낙관적 락에서 이미 사용).
- 겪은 주의점: UPDATE 빌더가 `updated_at = CURRENT_TIMESTAMP`를 넣어 `DATETIME(3)`의 밀리초를 버린다. 직접 지정해 해결했다. 이런 동작은 라이브러리 소스로 확인한다.
- 스키마 드리프트 테스트로 엔티티와 마이그레이션이 어긋나면 CI가 실패한다.

## 이 결정이 바뀌는 조건

- 팀 표준이 Prisma이거나, 복잡한 조회가 많아 컴파일 타임 타입 안전성의 이득이 크면 B.
- SQL을 세밀하게 통제해야 하는 쿼리가 대부분이면 Drizzle 같은 SQL 중심 도구(C).
