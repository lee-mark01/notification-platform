# 0001. 큐를 채널 × 유형으로 분리

- 상태: 채택 (2026-10-08)
- 관련: [상태 머신](../design/state-machine.md), 장애 시나리오 13

## 상황

마케팅 메일 1만 건을 보내는 도중에 회원가입 인증 메일이 들어오면, 인증 메일은 몇 초 안에 도착해야 한다. 인증 메일이 마케팅 뒤에 줄을 서면 사용자는 가입을 포기한다. 또 이메일(SES)과 푸시(FCM)는 Provider가 달라 처리량 한도, 장애, 지연이 서로 다르다.

## 선택지

| 선택지                                                                                                         | 장점                                                                                                                                       | 단점                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 채널 × 유형 4개 큐 (`email-transactional`, `email-marketing`, `push-transactional`, `push-marketing`) + DLQ | 큐마다 Worker 동시성·rate limit을 따로 정함. 한 큐가 밀리거나 Provider가 느려져도 다른 큐에 영향 없음. 큐별 대기열 길이가 그대로 지표가 됨 | 큐·Worker 설정이 4벌. 같은 Provider를 쓰는 큐끼리 계정 한도를 나눠 가져야 함                                                                                                                              |
| B. 단일 큐 + BullMQ `priority`                                                                                 | 설정이 하나                                                                                                                                | 우선순위는 **대기 순서**만 바꾼다. 이미 실행 중인 마케팅 job과 같은 Worker의 동시성 슬롯·rate limit을 공유하므로, 마케팅이 슬롯을 다 쓰고 있으면 인증 메일도 기다린다. Provider 장애도 모든 유형에 번진다 |
| C. 채널별 2개 큐                                                                                               | A보다 단순                                                                                                                                 | 같은 채널 안에서 마케팅과 인증 메일이 섞여 위 문제가 그대로 남음                                                                                                                                          |

## 결정

A. Dispatcher가 알림의 (channel, category)로 큐를 고른다. 큐 이름은 상수로 관리한다.

## 결과

- 좋은 점: 인증 메일 큐는 낮은 동시성으로도 마케팅과 무관하게 즉시 처리된다. 큐별 rate limit(`limiter: { max, duration }`)으로 마케팅만 천천히 보낼 수 있다.
- 감수할 점: SES 계정 발송 한도는 계정 전체에 걸리므로, 이메일 두 큐의 limiter 합이 계정 한도를 넘지 않게 정해야 한다. BullMQ의 limiter는 큐 단위라 계정 단위 한도를 자동으로 나눠 주지 않는다.
- 검증: Phase 5에서 마케팅 1만 건 등록 중 인증 메일의 대기 시간(`processedOn − timestamp`)을 단일 큐 구성과 비교한다(장애 시나리오 13).

## 이 결정이 바뀌는 조건

- 유형이 많아지면(예: 10개 이상) 큐를 계속 늘리기보다 가중치 기반 공정 스케줄링이나 테넌트별 큐로 간다.
- Provider 계정 한도가 빡빡해 큐 간 한도 배분이 자주 바뀌면, 큐 앞에 공용 토큰 버킷(예: Redis 기반 전역 rate limiter)을 둔다.
