# 0003. Outbox 대신 "커밋 후 큐 등록 + Sweeper"

- 상태: 채택 (2026-10-08)
- 관련: [상태 머신 — 큐 등록](../design/state-machine.md#큐-등록-t1), 장애 시나리오 2

## 상황

알림을 DB에 저장하는 것과 Redis 큐에 등록하는 것은 두 시스템이라 하나의 트랜잭션으로 묶을 수 없다. DB 커밋 후 Redis가 죽으면 알림은 저장됐는데 큐에는 없다(유실). 반대로 큐에 먼저 넣고 DB 커밋이 실패하면 존재하지 않는 알림이 발송된다.

## 선택지

| 선택지                                                                                                       | 장점                                                                    | 단점                                                                                                |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| A. 커밋 후 큐 등록 + Sweeper: 커밋 뒤 바로 등록하고, 등록 실패로 PENDING에 남은 알림을 주기 작업이 다시 등록 | 정상 경로가 빠름(커밋 직후 등록). 별도 테이블·상시 폴링 프로세스가 없음 | 등록 실패 시 Sweeper 주기만큼 지연. Sweeper와 Dispatcher가 같은 알림을 동시에 등록할 수 있음        |
| B. Transactional Outbox: 같은 트랜잭션에 이벤트 행을 쓰고, 별도 프로세스(relay)가 읽어 큐에 발행             | 유실 없음이 구조적으로 보장. 이벤트 순서·다중 소비자에 유리             | outbox 테이블, relay 프로세스, 발행 완료 표시·정리가 추가됨. 모든 알림이 relay 폴링 주기만큼 늦어짐 |
| C. CDC(Debezium 등)로 binlog를 읽어 발행                                                                     | 앱 코드 변경 없이 유실 없음                                             | Kafka·커넥터 등 인프라가 큼                                                                         |

## 결정

A. 사실상 **`notification` 테이블의 PENDING 상태가 Outbox 역할을 겸한다.** 알림 행 자체가 "아직 큐에 안 들어간 일"의 기록이므로 별도 outbox 테이블이 필요 없다.

## 결과

- 유실 방지: 알림은 커밋돼야만 존재하고, PENDING으로 남은 것은 Sweeper가 `ix_notification_status_updated_at`으로 찾아 다시 등록한다. Redis 장애 후 복구되면 유실 0건이어야 한다(장애 시나리오 2, chaos 스크립트로 검증).
- 중복 등록: Dispatcher와 Sweeper가 같은 알림을 동시에 등록해도 `jobId = notificationId`로 BullMQ가 중복 job을 만들지 않는다. job이 이미 지워진 뒤 재등록되더라도 Worker의 조건부 점유가 두 번째 처리를 막는다.
- 감수할 점: 등록 실패 시 Sweeper 주기(예: 30초)와 대기 기준(예: 1분)만큼 지연된다.

## 이 결정이 바뀌는 조건

- 알림 외에도 여러 서비스가 같은 이벤트를 받아야 하는 이벤트 기반 구조가 되면 B(또는 Kafka + C)로 간다.
- 이벤트 순서가 중요해지거나, 엔티티 상태와 별개로 "발행할 메시지"를 따로 관리해야 하면 B.
- OpenBake에서는 토스페이먼츠 웹훅 + 폴링 배치를 안전망으로 썼다. 이번 Sweeper도 같은 "정상 경로 + 주기적 안전망" 구조다.
