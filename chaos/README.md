# 장애 재현 스크립트

프로세스와 인프라를 실제로 멈추거나 죽여서 장애 시나리오 2, 6, 7을 재현한다.

각 스크립트는 다음 순서로 진행한다.

1. 전용 스택(`np-chaos`)을 새로 띄운다. MySQL, Redis, API, Worker로 구성된다.
2. 장애를 일으킨다.
3. 결과를 MySQL과 로그에서 세고, 기대와 다르면 0이 아닌 코드로 끝난다.

- 개발용 스택(`docker compose up`)과 볼륨·포트가 겹치지 않는다. 전용 스택의 API는 `localhost:13000`이다.
- 끝나면 전용 스택을 지운다. 남겨 두려면 `KEEP_STACK=1`을 붙인다.

필요한 것: Docker, bash(Windows는 Git Bash), curl

```bash
bash chaos/redis-down.sh      # 시나리오 2 (기본 20건)
bash chaos/worker-kill.sh     # 시나리오 6 (기본 20건)
bash chaos/worker-sigterm.sh  # 시나리오 7 (기본 40건)
```

## 구성

| 서비스       | 역할                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| api          | 요청만 받는다(`WORKERS_ENABLED=false`)                                        |
| worker       | 발송만 한다. 가짜 Provider가 건당 2초 걸려 job이 처리 중인 순간을 만들기 쉽다 |
| mysql, redis | 이 스택 전용                                                                  |

- 짧게 줄인 설정: 재시도 기본 1초, sweep 5초마다, PENDING 5초 이상이면 재등록
- 가짜 Provider는 실제로 보낼 때마다 `delivered notification=<id>`를 남긴다. 스크립트는 Worker 컨테이너의 모든 실행 로그에서 이 줄을 세어 중복 발송을 잰다.
- stall 감지는 Worker 로그의 `stalled`로 센다.

## 시나리오와 기대 결과

| #   | 스크립트            | 하는 일                                                | 통과 조건                                                |
| --- | ------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| 2   | `redis-down.sh`     | Redis 정지 → N건 접수 → Redis 재시작                   | 전부 202, 정지 중엔 PENDING, 복구 후 전부 SENT(유실 0)   |
| 6   | `worker-kill.sh`    | 발송 중 Worker `kill -9` → 재시작                      | 전부 SENT. stall 감지 수, 재점유 수, 중복 발송 수를 보고 |
| 7   | `worker-sigterm.sh` | 발송 중 Worker SIGTERM(`docker compose stop`) → 재시작 | 종료 후 SENDING 0, stall 0, 중복 0, 전부 SENT            |

시나리오 6의 중복 발송은 막는 대상이 아니라 재는 대상이다. Provider 호출을 마친 직후, 결과를 기록하기 전에 죽으면 lease가 끝난 뒤 다시 보낸다(at-least-once, ADR-0002).

## 측정 기록

| 날짜       | 시나리오 | 결과                                                                                                                         |
| ---------- | -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 2026-10-09 | 2        | 20건 접수(Redis 정지 중) → 복구 후 20건 SENT, 유실 0. 복구 후 약 11초                                                        |
| 2026-10-09 | 6        | 처리 중 6건에서 kill → stall 6건 감지, 6건 재점유, 20건 모두 SENT, 중복 발송 0건. 재시작 후 약 73초(stall 감지 + lease 60초) |
| 2026-10-09 | 7        | 처리 중 10건에서 SIGTERM → 3초 안에 종료, 남은 SENDING 0, stall 0, 중복 0, 40건 모두 SENT                                    |
| 2026-10-09 | 2        | 재실행: 20건 접수 → 복구 후 20건 SENT, 유실 0 (README 캡처)                                                                  |
| 2026-10-09 | 6        | 재실행: 처리 중 8건에서 kill → stall 8건, 8건 재점유, 20건 SENT, 중복 0. 재시작 후 약 71초 (README 캡처)                     |

시나리오 6의 중복 0건은 이번 실행에서 kill이 2초짜리 발송 도중에 떨어졌기 때문이다. kill 시점이 "발송 완료 ~ 결과 기록" 사이에 걸리면 그 건은 중복으로 잡힌다.
